## 一、需求分析

### 1.1 项目背景

在校大学生在备考过程中普遍面临以下问题：

1. **题源分散**：纸质习题、电子文档、各类 App 各自独立，缺少统一管理
2. **缺乏反馈**：做完题后无法及时知道对错，更看不到错在哪里、为什么错
3. **盲目刷题**：不清楚自己哪些学科、哪些章节薄弱，导致复习效率低
4. **缺少模拟**：无法在考前进行限时自测，难以评估真实水平

现有的在线题库多为商业产品，功能冗余且需付费；而学校自建平台又常常
只提供题目下载，缺少作答与统计能力。

### 1.2 建设目标

设计并实现一个**面向在校大学生**的在线刷题系统，具备：

- 覆盖多学科的结构化题库，支持按学科 / 章节 / 题型 / 难度筛选
- 作答即时判分，并提供解题思路解析
- 自动收集错题，支持订正追踪
- 限时模拟考试，给出成绩与逐题回顾
- 学习数据统计，定位薄弱环节

### 1.3 功能需求

| 编号 | 功能模块 | 功能描述 | 优先级 |
| --- | --- | --- | --- |
| F1 | 用户注册 | 用户名 + 密码注册，密码加密存储 | 高 |

| F5 | 模拟考试 | 随机抽题、限时、交卷出分 | 高 |
| F6 | 错题本 | 答错自动收录，答对标记已订正 | 高 |
| F7 | 收藏夹 | 手动收藏重点题目 | 中 |
| F8 | 学习统计 | 累计答题、正确率、学科掌握度 | 中 |

### 1.4 非功能需求

| 类别 | 要求 |
| --- | --- |
| **安全性** | 密码不可明文存储；用户间数据隔离；防止暴力破解 |
| **易用性** | 界面简洁，答题流程不超过 2 次点击；移动端可用 |
| **性能** | 常规查询响应时间 < 500 ms；题库 100+ 题规模下无需分页优化 |
| **可维护性** | 前后端分离；分层架构；配置与代码分离 |

## 二、系统设计

### 2.1 总体架构

系统采用**前后端分离**的三层架构：

```
┌──────────────────────────────────────────────┐
│                  浏览器                        │
│   Vue3 SPA（Vue Router + Pinia + Axios）      │
└───────────────────┬──────────────────────────┘
                    │ HTTP / JSON
                    │ Authorization: Bearer <token>
┌───────────────────▼──────────────────────────┐
│              Spring Boot 应用                  │
│  ┌────────────────────────────────────────┐  │
│  │ Controller 层：接收请求、参数校验        │  │
│  ├────────────────────────────────────────┤  │
│  │ Service 层：业务逻辑、事务控制           │  │
│  ├────────────────────────────────────────┤  │
│  │ Repository 层：Spring Data JPA          │  │
│  └────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────┐  │
│  │ 横切：AuthInterceptor（鉴权）           │  │
│  │       GlobalExceptionHandler（异常）    │  │
│  └────────────────────────────────────────┘  │
└───────────────────┬──────────────────────────┘
                    │ JDBC
┌───────────────────▼──────────────────────────┐
│         MySQL 8.0 / H2（开发）                │
└──────────────────────────────────────────────┘
```

**分层职责**

| 层次 | 职责 | 对应包 |
| --- | --- | --- |
| 表现层 | 路由、页面渲染、用户交互 | `frontend/src/views`、`components` |
| 接口层 | 请求路由、参数校验、响应封装 | `controller` |
| 业务层 | 核心业务逻辑、事务边界 | `service` |
| 持久层 | 数据访问、对象映射 | `repository`、`entity` |
| 横切层 | 鉴权、异常处理、跨域 | `security`、`common`、`config` |

### 2.3 核心流程设计

#### 2.3.1 登录鉴权流程

```
用户                前端              后端                 数据库
 │                   │                 │                    │
 ├─ 输入账号密码 ───>│                 │                    │
 │                   ├─ POST /login ──>│                    │
 │                   │                 ├─ 查询用户 ────────>│
 │                   │                 │<──── 用户记录 ─────┤
 │                   │                 │                    │
 │                   │                 ├─ 检查是否锁定      │
 │                   │                 ├─ BCrypt 校验密码   │
 │                   │                 │                    │
 │                   │                 ├─ 生成随机 token ──>│
 │                   │                 │<──── 保存成功 ─────┤
 │                   │<── token + 用户信息 ─┤                │
 │                   ├─ 存入 localStorage  │                │
 │<─ 跳转首页 ────────┤                 │                    │
 │                   │                 │                    │
 ├─ 访问受保护接口 ──>│                 │                    │
 │                   ├─ Bearer token ──>│                    │
 │                   │                 ├─ 拦截器校验 token ─>│
 │                   │                 │<──── 有效 ─────────┤
 │                   │<── 业务数据 ─────┤                    │
```

**设计要点**

- 采用**服务端会话**而非 JWT：token 存库便于主动失效（登出即删），
  且能实现「同一账号在多设备登录」的独立会话管理
- 密码用 BCrypt 哈希（自带随机盐），同一密码每次加密结果不同，
  即使数据库泄露也无法直接还原明文

#### 2.3.2 判分流程

```
提交答案 (questionId, answer)
    │
    ├─ 查题目，取 type 字段
    │
    ├─ type == "fill" ──> 取答案文本 ──> trim + 忽略大小写比对
    │
    └─ 其他题型 ──> 把正确答案 JSON 解析为下标集合
                    ──> 把用户答案 JSON 解析为下标集合
                    ──> 比较两个集合是否相等
                    │
    ├─ 更新答题记录（attempts +1，正确则 correctCount +1）
    │
    ├─ 答错 → 写入/更新错题本（resolved = false）
    └─ 答对 → 若在错题本中则标记 resolved = true
```

**设计说明**

- 用**集合比较**而非数组比较，使多选题的答案顺序不影响判分结果
- 填空题忽略首尾空白与大小写，避免因输入格式差异误判
- 判分与记录更新在同一事务内，保证数据一致

#### 2.3.3 模拟考试流程

```
设置参数（范围/题数/限时）
    │
    ├─ 后端随机抽题（按范围过滤后乱序取前 N 条）
    │
    ├─ 前端开始倒计时
    │      └─ 归零 → 自动交卷
    │
    ├─ 用户逐题作答（答案暂存前端 answers 对象，不请求后端）
    │
    └─ 交卷
          ├─ 遍历所有题目，逐题调用 /practice/submit
          ├─ 统计答对数，计算百分制得分
          ├─ 保存考试记录
          └─ 展示成绩单与逐题解析
```

**设计说明**

- 考试过程中答案暂存前端，**交卷时才逐题提交**：
  避免每选一个选项都发请求，减少网络往返
- 逐题提交复用了练习模块的判分逻辑，同时也把错题写入了错题本，
  保证数据一致

### 2.4 安全设计

| 威胁 | 防护措施 |
| --- | --- |
| 密码泄露 | BCrypt 加盐哈希存储，数据库不存明文 |
| 暴力破解 | 连续失败 5 次锁定账号 10 分钟 |
| 会话劫持 | token 为 32 字节安全随机数；设有效期；登出即失效 |
| 越权访问 | 所有查询与更新都带 `userId` 条件，从 token 解析而非前端传入 |
| SQL 注入 | 全部使用 JPA 参数化查询，不拼接 SQL 字符串 |
| XSS 攻击 | 公式渲染 `trust: false`；文本渲染先做 HTML 转义 |
| 跨域滥用 | CORS 白名单限定前端来源 |

> **关键设计**：`userId` 一律从服务端解析的 token 中取，
> **绝不接受前端传入的 userId**，这是防越权的根本手段。
> 若前端可以指定 userId，攻击者改一个数字就能读他人的错题本与统计。

#### 表 3-3 题目表 `quiz_question`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |

| answer | TEXT | NOT NULL | 正确答案 JSON |
| analysis | TEXT | | 解析 |
| knowledge | TEXT | | 知识点数组 JSON |

**设计说明：为什么 options / answer 用 JSON 字符串？**

四种题型的选项与答案结构不同：

| 题型 | options | answer |
| --- | --- | --- |
| 单选题 | `["A","B","C","D"]` | `[1]` |
| 多选题 | `["A","B","C","D"]` | `[0,2]` |
| 判断题 | `["正确","错误"]` | `[0]` |
| 填空题 | `null` | `"1"` |

若拆成 `question` + `question_option` 两张表，虽然更符合范式，
但会让查询与判分逻辑复杂化（每次都要联表查选项）。
考虑题库规模在千级、且选项总是一起读取，**用 JSON 字段换取查询简洁**
是更务实的选择。这是典型的「反范式设计」权衡。

#### 表 3-4 答题记录表 `quiz_record`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK | 主键 |
| user_id | BIGINT | NOT NULL, FK | 用户 |
| question_id | BIGINT | NOT NULL, FK | 题目 |
| attempts | INT | NOT NULL | 作答总次数 |
| correct_count | INT | NOT NULL | 答对次数 |
| last_correct | TINYINT(1) | NOT NULL | 最近是否答对 |
| last_answer | TEXT | | 最近提交答案 |
| last_at | DATETIME | NOT NULL | 最近作答时间 |

**唯一索引** `(user_id, question_id)`：保证一个用户对一道题只有一行记录，
答题时「存在则累加，不存在则插入」，避免记录膨胀。

#### 表 3-5 错题/收藏表 `quiz_mark`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK | 主键 |
| user_id | BIGINT | NOT NULL, FK | 用户 |
| question_id | BIGINT | NOT NULL, FK | 题目 |
| type | VARCHAR(20) | NOT NULL | WRONG / FAVORITE |
| resolved | TINYINT(1) | NOT NULL | 是否已订正 |
| created_at | DATETIME | NOT NULL | 加入时间 |

**设计说明：为什么错题和收藏合为一张表？**

两者的结构完全一致（都是「用户标记了某道题」），只是语义不同。
合并后新增标记类型无需建新表，查询时按 `type` 过滤即可。
若将来需要「标记为待复习」「标记为难题」等，只需增加 type 取值。

| 字段 | 类型 | 约束 | 说明 |

| scope | VARCHAR(100) | NOT NULL | 考试范围 |
| total | INT | NOT NULL | 题目总数 |
| correct_count | INT | NOT NULL | 答对数 |

### 3.3 索引设计

| 表 | 索引 | 用途 |
| --- | --- | --- |
| sys_user | `uk_username` | 登录时按用户名查询，且保证唯一 |
| sys_session | `uk_token` | 每次请求都要按 token 查会话，必须高效 |
| sys_session | `idx_user` | 登出时清理该用户全部会话 |
| quiz_question | `idx_subject` | 按学科筛选 |
| quiz_question | `idx_subject_chapter` | 按学科+章节组合筛选 |
| quiz_question | `idx_type` | 按题型筛选 |
| quiz_record | `uk_user_question` | 答题时定位记录 + 防重复 |
| quiz_mark | `uk_user_question_type` | 防重复标记 |
| quiz_mark | `idx_user_type` | 查询某用户的错题或收藏列表 |
| quiz_exam | `idx_exam_user` | 查询考试历史 |

**索引设计原则**：为「高频查询条件」与「唯一性约束」建索引。
`sys_session.token` 是全系统访问最频繁的字段（每个请求都要查），
没有索引时每次都是全表扫描，用户量增长后会成为瓶颈。

## 四、系统实现

### 4.1 后端关键实现

#### 4.1.1 统一响应封装

所有接口返回统一结构，前端只需判断 `code`：

```java
public class ApiResult<T> {
    private int code;       // 0 = 成功
    private String message;
    private T data;
}
```

对应前端 axios 响应拦截器：

```javascript
api.interceptors.response.use((res) => {
  const body = res.data
  if (body.code !== 0) return Promise.reject(new Error(body.message))
  return body.data          // 直接返回业务数据
})
```

这样业务代码里 `await api.getUserId()` 拿到的是纯数据，
无需每次写 `res.data.data`。

#### 4.1.2 鉴权拦截器

```java
public boolean preHandle(HttpServletRequest req, ...) {
    String token = resolveToken(req);        // 读 Authorization 头
    if (token == null) return unauthorized();

    Session session = sessionRepo.findByToken(token)
        .orElseThrow(...);
    if (session.getExpiresAt().isBefore(now())) {
        sessionRepo.delete(session);          // 顺手清理过期会话
        return unauthorized();
    }

    req.setAttribute("currentUser", userRepo.findById(session.getUserId()));
    return true;
}
```

Controller 通过 `@RequestAttribute("currentUser") User user` 拿到当前用户，
**userId 完全由服务端决定**。

#### 4.1.3 判分实现

```java
public boolean judge(Question q, Object submitted) {
    if ("fill".equals(q.getType())) {
        String expected = parseFillAnswer(q.getAnswer());
        String actual = String.valueOf(submitted).trim();
        return !actual.isEmpty() && actual.equalsIgnoreCase(expected.trim());
    }
    Set<Integer> expected = parseIndexSet(q.getAnswer());
    Set<Integer> actual = parseIndexSet(toJson(submitted));
    return !expected.isEmpty() && expected.equals(actual);
}
```

`parseIndexSet` 兼容 `[1]`、`["1"]`、`1` 等多种格式，
避免因 JSON 类型不一致导致判分错误（例如前端传字符串 `"1"` 而后端存数字 `1`）。

#### 4.2.2 公式渲染组件

题库含大量数学公式，需要把 `$\lim_{x \to 0}$` 渲染为排版后的数学式。

实现思路：按定界符切分文本，公式段交给 KaTeX，文本段做 HTML 转义。

```javascript
// 行内 $...$：只要能找到配对的 $ 且内部非空，就按公式处理
if (src[i] === '$') {
  const end = src.indexOf('$', i + 1)
  if (end > i + 1) {
    out += katex.renderToString(src.slice(i + 1, end), {
      displayMode: false,
      throwOnError: false,
      trust: false          // 禁用 \href 等危险命令，防 XSS
    })
    i = end + 1
    continue
  }
}
```

**踩过的坑**：最初为避免把「价格 $5」误判为公式，
规则写成「`$` 后不能跟数字」。结果数学题选项里的 `$0$`、`$1$`
（纯数字公式）也被拦掉了，显示成原始的 `$0$` 文本。

修正为「配对且内部非空」判定后：
- `$0$`、`$1$` 正常渲染 ✓
- 没有配对 `$` 的自然文本仍不误判 ✓

这个问题的验证方式是**真实浏览器截图检查**——单元测试只验证了
「渲染函数返回非空字符串」，并没有检查「选项里的公式是否正确显示」。

#### 4.2.3 答案状态管理

练习页需要处理四种题型的交互差异：

| 题型 | 交互 | 提交时机 |
| --- | --- | --- |
| 单选题 | 点选项 | 立即提交并判分 |
| 多选题 | 多选 | 点「提交答案」按钮 |
| 判断题 | 点选项 | 立即提交 |
| 填空题 | 输入框 | 回车或点「提交答案」 |

用 `pendingMulti` 标志区分多选题的暂存状态，
避免多选题每勾一个选项就触发判分。

### 4.3 测试与验证

| 测试类型 | 工具 | 用例数 | 覆盖内容 |
| --- | --- | --- | --- |
| 接口测试 | Node.js 脚本 | 35 | 题库查询、注册登录、鉴权、判分、错题、统计、考试 |
| 浏览器端到端 | Edge Headless + CDP | 28 | 页面渲染、注册流程、公式渲染、交互、无 JS 异常 |

**为什么需要浏览器测试？**

接口测试只能证明「后端返回了正确的数据」，
但无法发现：

- 前端组件渲染错误（如公式未渲染）
- 事件绑定失效（按钮点了没反应）
- 运行时 JS 异常

本项目用 CDP（Chrome DevTools Protocol）驱动真实浏览器，
模拟真实点击与输入，并监听 `Runtime.exceptionThrown` 事件捕获未处理异常。
这一层测试抓出了接口测试完全看不到的渲染问题。
